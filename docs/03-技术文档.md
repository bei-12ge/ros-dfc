## 3. 关键技术点

### 3.1 继承与多态：一套抽象，两类节点，一种扩展

`Node` 只声明"必须有名字、必须能初始化、必须能关闭"，把具体注册动作留给子类：

```cpp
class Node {
public:
    virtual void init() = 0;       // 纯虚：子类必须给出自己的注册语义
    virtual void shutdown() = 0;
protected:
    void markRunning(bool running) noexcept { running_ = running; }
private:
    const std::string name_;       // const 成员：构造后不可改
    bool running_ = false;
};
```

这样 `ROS::shutdownAll()` 用 `std::vector<Node*>` 统一遍历，**不需要知道谁是发布者、谁是订阅者**——这就是"依赖倒置"的落地：核心依赖抽象，而非具体类型。

多态还被用到消息层：`SensorMessage` 覆盖 `typeName()/toString()`，而核心转发只传 `shared_ptr<const Message>`，**动态类型在传递过程中不丢失**（由测试 `bonus_sensor` 用 `dynamic_cast` 验证）。

### 3.2 单例：为什么用函数内静态变量

```cpp
ROS& ROS::instance() {
    static ROS core;   // C++11 起局部静态初始化线程安全（magic static）
    return core;
}
ROS(const ROS&) = delete;
ROS& operator=(const ROS&) = delete;
```

对比三种写法：

| 方案 | 问题 |
| --- | --- |
| 全局变量 `ROS g_core;` | 跨编译单元初始化顺序不确定，可能在其他静态对象构造时尚未就绪 |
| 裸 `new` + 指针 | 需要手动 delete，或故意泄漏；无法保证首次调用线程安全 |
| **函数内静态（采用）** | 首次调用才构造、线程安全、析构顺序跟随作用域，代码最短 |

代价：析构发生在 `main` 返回之后，因此 `Node` 析构里访问核心必须 `try/catch` 兜底（见 3.4）。

### 3.3 所有权模型：核心"借用"，调用方"拥有"

```cpp
std::unordered_map<std::string, Node*> nodes_;            // 非拥有指针
std::unordered_map<std::string, std::vector<Publisher*>> publishers_;
```

- 节点对象由 `main` 的 `unique_ptr` 或测试的栈对象持有，核心**只借用**；
- 好处：动态删除节点时不会 delete 掉调用方仍在用的对象（防止 use-after-free）；
- 保证不悬空的手段是 `~Node()` 兜底注销 + `shutdown()` 幂等。

消息则相反：`std::shared_ptr<const Message>` 让一条消息被 k 个订阅者共享，**O(1) 传递、只读防篡改**。`const` 很关键——多订阅者并发读同一对象，若可写就会产生数据竞争。

### 3.4 线程安全：锁只保护表，回调一定在锁外

这是本项目最需要讲清楚的设计。

```cpp
size_t ROS::publish(const std::string& topic, const std::shared_ptr<const Message>& message) {
    std::vector<Subscriber*> targets;
    {
        std::lock_guard<std::recursive_mutex> lock(mutex_);
        // ... 校验与查找
        if (subIt != subscribers_.end()) targets = subIt->second;   // ① 拷副本
    }                                                               // ② 解锁
    for (auto* subscriber : targets) subscriber->receive(message);  // ③ 锁外分发
    return targets.size();
}
```

如果第 ③ 步在锁内执行，会出现两类事故：

1. **死锁/长阻塞**：订阅者回调里再 `publish`，或回调耗时长，整个核心被卡住；
2. **迭代器失效**：回调里 `shutdown` 某个节点会修改 `subscribers_` 的 vector，正在遍历的迭代器立刻失效（UB）。

改用递归锁（`recursive_mutex`）是为了让 `registerPublisher` 内部调用 `registerNodeUnlocked` 这类**同线程嵌套加锁**不死锁；但它**不替代**"锁外回调"这条纪律。

其余并发点：

| 位置 | 手段 | 原因 |
| --- | --- | --- |
| 发布/接收计数 | `std::atomic<size_t>` | 只需原子自增，不值得为统计抢锁 |
| 订阅者回调替换 | 独立 `std::mutex` + 取副本 | 回调可在运行期被 `setCallback` 替换 |
| 时间格式化 | `localtime_r` / `localtime_s` | `std::localtime` 返回共享静态缓冲区，多线程下会互相覆盖 |
| 日志写入 | `Logger` 内部 `recursive_mutex` | 多线程写同一 `ofstream` 必须串行化 |

并发用例：4 线程 × 500 条发布，2 个订阅者各自精确收到 2000 条（`ros.四线程并发发布两订阅者计数一致`），ASan/UBSan 下无报告。

### 3.5 异常体系：让"错误"可被程序识别，而不只是打印

```cpp
class RosException : public std::runtime_error {   // 继承标准异常 → 兼容既有 catch
public:
    RosException(std::string module, std::string code, LogLevel level, const std::string& msg);
    ...
};
NodeException NodeException::emptyName() {          // 静态工厂：错误码只在定义处出现一次
    return NodeException("NODE-001", "节点名称不能为空或全为空白字符");
}
```

三个设计取舍：

1. **继承 `std::runtime_error`**：第三方或旧代码写 `catch (const std::exception&)` 也能兜住，不会漏到 `std::terminate`。
2. **带 `code` 与 `level`**：日志可分级、测试可断言（`CHECK_THROWS_CODE("NODE-001", ...)` 就是靠它）。
3. **静态工厂而非公开构造错误码字符串**：调用方拿不到"随手编"的错误码，保证码表与文档一致。

**异常安全**：`Publisher::init()` 先注册、成功后才 `markRunning(true)`；若注册抛 `NODE-002`，对象仍是"未运行"状态，不会留下半注册的脏数据（对象析构时也不会误注销别人的表项）。

### 3.6 回调：`std::function` + 异常隔离

```cpp
try {
    callback(*this, message);
} catch (const std::exception& ex) {
    Logger::instance().error("SUB", "订阅者回调抛出异常，已隔离: 节点=" + name() +
                                        ", 原因=" + ex.what());
}
```

一条"坏"的业务回调不能拖垮整条话题的广播：异常在订阅者内部被吞掉并记 ERROR，发布者与其他订阅者不受影响（用例 `subscriber.回调抛出异常被隔离且不影响其他订阅者` 专门验证）。

### 3.7 日志分级与"绝不因日志失败而中断业务"

```cpp
bool Logger::addFileSink(const std::string& path) {
    // ... 打开失败时不抛异常
    warn("LOGGER", "日志文件不可写，已降级为仅控制台输出: " + path);
    return false;
}
```

日志是**观测手段**，不是业务流程。磁盘满、路径无权限都只降级为控制台输出，业务继续。写入用 `std::ios::app` 追加 + 每条 `flush()`，保证进程被 kill 时已输出的日志不丢。

## 4. 线程模型

```
主线程 ──┬─ init/shutdown/publish/test 调用
         └─ 订阅者回调（默认在发布线程栈内同步执行）
并发发布线程（测试中 4 个）── ROS::publish（加锁取副本 → 锁外分发）
```

- **v1 没有后台线程**：发布是"同步分发、异步语义"。发布者不等应答，但回调仍在发布调用栈内执行，因此日志顺序天然可读、时序可复现。
- 代价：回调耗时直接叠加到发布耗时。需求 NFR-4 已限定"回调应轻量"，v2 可引入"消息队列 + 分发线程"（架构文档 §9 已预留扩展点）。

## 7. 编码规范约定

1. 头文件一律 `#pragma once`，且保持"自包含"（单独 include 也能编译）；
2. 所有成员 `private`，只读接口返回 `const&` 或值；**没有 setter 的类就是不可变类**；
3. 资源管理只用 RAII：`std::lock_guard`、`std::ofstream`、`unique_ptr/shared_ptr`，无 `new`/`delete`（`main` 中也用 `make_unique`）；
4. 函数参数按"值传递 + `std::move`"或 `const&`，避免多余拷贝；
5. 每个 `.cpp` 只包含自己需要的头文件，依赖方向从上层指向下层；
6. 注释解释"为什么"，不复述"是什么"；关键决策在架构文档中留痕。

## 8. 已知限制与改进方向

| 限制 | 影响 | 改进思路 |
| --- | --- | --- |
| 回调在发布线程内执行 | 慢回调拖慢发布 | 订阅者侧加有界队列 + 独立分发线程 |
| 日志同步写 | 高频场景有开销 | 异步日志（后台线程 + 环形缓冲） |
| 时间戳精度到秒 | 高频消息时间戳重复 | 增加毫秒（`%03d` 或 `steady_clock` 相对时间） |
| 单进程 | 无法跨机 | 抽 `Transport` 接口，实现 TCP/共享内存版本 |
| 无消息序列化 | 不能落盘回放 | `Message::serialize()` + `rosbag` 简易实现 |
| 服务无超时 | 处理函数阻塞会卡调用方 | `call()` 增加超时参数（需异步服务端配合） |
