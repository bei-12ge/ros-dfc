# 答辩准备：讲解稿、演示脚本与高频问答

> 用途：答辩现场按此顺序讲，控制在 6~8 分钟（讲解 3 分钟 + 演示 3 分钟 + 问答 2 分钟）。
> 原则：**先讲"我解决了什么问题"，再讲"我怎么解决"，最后证明"它真的能跑"**。

## 一、3 分钟讲解稿（可直接背）

### 0:00–0:30 一句话开场

"我用 C++17 写了一个单进程的迷你 ROS 内核 `ros_sim`。它不复刻 ROS 的 API，而是复刻 ROS 最核心的那套模型：**节点、话题、消息、发布订阅路由**，并且把异常、日志、并发这些工程问题都做了真实处理。48 个自动化用例全部通过。"

### 0:30–1:20 系统结构与两个关键抽象

"整个系统分四层：应用层的 `main` 和测试、业务层的四个节点类、核心层的 `ROS` 单例、基础层的消息/异常/日志。

两个关键抽象决定了整个代码形态：

第一，**`Node` 抽象基类**。它只声明三件事：有唯一名字、`init()`、`shutdown()` 是纯虚。发布者和订阅者都继承它并各自实现注册语义。这样核心的 `shutdownAll()` 拿一个 `vector<Node*>` 就能统一关闭所有节点，**不需要知道谁是发布者**——这是依赖倒置。

第二，**`Message` 是不可变对象**。内容加时间戳，构造时就打好 `YYYY-MM-DD HH:MM:SS`，只有 const getter 没有 setter。转发时用 `shared_ptr<const Message>`：一条消息给 k 个订阅者共享，O(1) 传递，而且 const 保证多订阅者并发读不会写坏数据。"

### 1:20–2:20 三个技术难点（重点，评委会问）

"难点一：**单例怎么做**。我用的是函数内静态变量 `static ROS core;`，C++11 起这是线程安全且延迟初始化的，比全局变量没有初始化顺序问题，比裸 new 不需要手动释放。代价是它的析构在 main 之后，所以 `Node` 析构里访问核心必须 try/catch 兜底。

难点二：**锁粒度**。这是最容易写错的地方。我的规则是：**锁只保护三张映射表，回调一定要在锁外执行**。`publish` 里先加锁把订阅者列表**拷一份副本**，解锁，再分发。如果持锁分发，订阅者回调里再 publish 就会死锁；更严重的是回调里 shutdown 节点会修改 vector，正在遍历的迭代器直接失效，属于未定义行为。

难点三：**异常分级**。我定义了 `RosException` 继承 `std::runtime_error`，下面挂 `NodeException/TopicException/MessageException/ServiceException`，每个异常带模块、错误码、日志级别。所以它既能被 `catch (const std::exception&)` 兜住，又能被日志系统按 INFO/WARN/ERROR 分级输出，还能被测试用错误码精确断言。"

### 2:20–2:50 加分项

"除了必做，我还实现了四个加分项：`SensorMessage` 自定义消息（温度/湿度，30 行代码，核心转发层零改动）；`ServiceServer/ServiceClient` 同步请求-响应；运行期 `removeNode` 动态删节点；以及日志文件持久化。异常部分还做了统一捕获和错误码表。"

### 2:50–3:00 收尾

"验证方面：48 个用例 114 个断言全绿，ASan/UBSan 零报告；1 万条发布在 1 个订阅者时 15 毫秒，符合 NFR 的 100 毫秒要求。整个过程是 9 次增量提交，从文档到骨架到核心到加分项到测试，每一步都能编译。"

## 三、高频问答（按被问概率排序）

### Q1：为什么用单例？不用会怎样？

ROS 核心维护的是**全局唯一的注册表**——话题到订阅者的映射只能有一份，否则 A 发布者的消息和 B 订阅者的注册就不在一个世界里。单例还带来两个实际好处：任何节点 `init()` 时不必层层传参，`ROS::instance()` 随手可用；关闭时能一次遍历全部节点。

换个角度，如果不用单例，你就得在 `main` 里创建核心再注入给每个节点，或者用全局变量——前者啰嗦，后者有初始化顺序问题。

### Q2：为什么锁是 `recursive_mutex`？会不会掩盖问题？

因为 `registerPublisher` 内部要调 `registerNode`，两者都需要表锁，同线程嵌套加锁。用普通 `mutex` 就得把锁拆成两把或者手工传递"已加锁"状态，反而更容易错。

我承认递归锁有"掩盖调用环"的风险，所以配了两条纪律：一是**加锁范围内只做表操作**，不做日志之外的任何业务；二是**回调、服务处理一律在锁外**。这两条写进了架构文档，评审时是硬约束。

### Q3：`publish` 为什么"拷贝一份订阅者列表"？

因为回调里可能改变这张表。比如某个订阅者收到消息后决定自己下线（`shutdown`），如果我还拿着 `subscribers_` 里 vector 的迭代器在遍历，vector 一 `erase` 迭代器就失效，是未定义行为——可能崩，也可能静默错乱。拷一份副本（`vector<Subscriber*>`）代价很小，换来的是分发过程不受表变更影响。

### Q4：消息为什么用 `shared_ptr<const Message>`，不用引用或值传递？

三个原因：一是 **k 个订阅者共享同一份**，值传递要拷贝 k 次；二是 **`const` 防篡改**，多订阅者并发读同一对象时，若可写就有数据竞争；三是 **生命周期安全**，回调可以把消息存起来，引用计数保证不悬空。

面试常追问："那你 `publish(const Message&)` 这个重载呢？"——那是给"我手上就有一个栈上消息"的便利用法，内部会拷贝一次。注意传 `SensorMessage` 时必须用 `shared_ptr` 版本，否则按基类引用传参会**切片**，多态信息丢失。

### Q5：怎么保证"非法输入程序不崩溃"？举一个最典型的。

三道防线：**构造时校验**（空名、空话题、空内容在构造函数里就抛）、**使用时校验**（未 init 就 publish 抛 `NODE-003`，向未声明话题转发抛 `TOPIC-002`）、**顶层兜底**（`main` 里 `catch (const RosException&)` 记日志，`catch (const std::exception&)` 记未知异常，`catch (...)` 记最后一道）。

演示里连续做 6 个非法操作，进程照常往下跑，就是这三道防线的效果。

### Q6：异常为什么继承 `std::runtime_error`？

为了让"老代码"也能兜住它。如果自定义异常直接继承 `std::exception`，那 `catch (const std::runtime_error&)` 是抓不到的。继承 `runtime_error` 相当于兼容了绝大多数既有 catch 习惯，同时我又能通过 `code()` 做精确判断。

### Q7：回调里抛异常会怎样？

被 `Subscriber::receive` 内部 `try/catch` 吞掉并记一条 ERROR，**不影响发布者，也不影响同话题的其他订阅者**。这是刻意的：一条坏消息不该打断整条广播链路。有专门用例 TC-303 验证。

### Q8：怎么证明线程安全？不只是"我觉得"。

三层证据：一是设计上锁只包表、计数用 `atomic`；二是 TC-514 用 4 线程 × 500 条并发发布，两个订阅者各自**精确**收到 2000 条，不是"大概对"；三是同一套用例在 `-fsanitize=address,undefined` 下重跑，零报告。如果存在数据竞争，TSan 会更直接，但 ASan/UBSan 至少能抓出内存越界与 UB。

### Q9：性能和真实 ROS 比怎么样？瓶颈在哪？

1 个订阅者时单条 1.5 微秒、约 65 万条/秒；3 个订阅者 2.4 微秒。真实 ROS 走 TCPROS，还有序列化与网络栈，量级完全不同，这里没有可比性——我的目标是把**内存模型**讲清楚。

已知瓶颈是日志字符串拼接（每条消息要拼 4~5 段中文），以及回调在发布线程内同步执行。v2 我预留了两个改进点：日志异步化、订阅者侧有界队列 + 独立分发线程。

### Q10：为什么监控数据里"话题无订阅者"只 WARN 不抛异常？

因为这在 ROS 语义里是**合法状态**：发布者可以先启动，订阅者后启动。如果这里抛异常，正常的分步启动就会被判为错误。真正非法的只有"这个话题从没被任何节点声明过"，那个才抛 `TOPIC-002`。

### Q11：节点对象谁负责销毁？会不会悬空？

核心只存**非拥有指针**，节点由调用方（`main` 的 `unique_ptr` 或测试的栈对象）持有。防悬空有三道：`Node` 析构自动注销、`shutdown()` 幂等、核心关闭后拒绝新注册。选非拥有是刻意的——如果核心用 `unique_ptr` 拥有节点，"运行期删除节点"就等于删掉调用方还在用的对象，风险更大。

### Q12：为什么测试框架自己写，不用 gtest？

作业环境不保证有网络装依赖，我不想让评审因为"装不上 gtest"而跑不起来。自研框架 100 行，支持用例注册、数值/字符串断言、**按错误码断言异常**、失败定位到文件行号，够用且零依赖。真要接 CI，退出码非 0 就能拦住。

### Q13：如果让你扩展成真正的跨进程 ROS，怎么做？

核心是把 `ROS::publish` 里的"本地函数调用"换成"传输层投递"。我会抽一个 `Transport` 接口（`send(topic, bytes)` / `subscribe(topic, callback)`），本地实现走内存，网络实现走 TCP + 消息序列化。节点层、消息层、异常层都不用改——这正是当初把 `Message` 做成"可序列化载体"的原因。

### Q14：代码里有没有你觉得还不够好的地方？（诚实题）

有三处：
1. `Publisher::publish(const Message&)` 存在切片风险，理想做法是删掉这个重载，只留 `shared_ptr` 版本；
2. 时间戳只到秒，高频消息会重复，应该加毫秒；
3. 服务调用没有超时，服务端卡住会拖住客户端，v2 要加超时参数。

我把这些都写进了技术文档"已知限制"，不藏。

### Q15：增量提交是怎么做的？会不会是最后一次性拆的？

每个提交都是**能编译、能跑**的最小闭环：先文档（需求+架构）→ 骨架 → 异常与日志 → 消息 → 节点与核心 → 自定义消息 → 服务 → 动态节点 → 测试 → 补齐文档。提交信息用 `feat(scope):` / `test:` / `docs:` 前缀，能看出功能边界。答辩时可以现场 `git show` 任意一个提交，diff 与提交信息是对得上的。
